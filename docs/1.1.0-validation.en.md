# GPur 1.1.0 Validation Record

[日本語](1.1.0-validation.md) | [English](1.1.0-validation.en.md)

**Status: 2026-10-09 · Minecraft 26.2 · GPur SNAPSHOT1.1.0**

Runner and independent audit agents used GPT-6 luna with xhigh reasoning. The host was Windows 11 Pro (build 26200), an Intel Core i9-11900KF (8 cores / 16 logical processors), approximately 96 GiB RAM, OpenJDK 25.0.2, and NVIDIA driver 581.57; both cards have 8 GiB VRAM. Background applications and power state were not controlled, so these short runs are not isolated performance experiments.

This record separates CPU code validation, simulated world-generation parity, standalone physical-GPU checks, and production performance evidence. The final CPU suite and physical-device runs are summarized below. No production TPS or server-throughput improvement has been established.

## Recorded CPU validation

The final default run used OpenJDK 25.0.2. Patch application and build passed. It aggregates 142 Gradle test-result XML files: 9,380 tests, zero failures, zero errors, and 28 skipped. The opt-in GPU tests were skipped as configured; the shipped FP64 shader compiled to SPIR-V on the CPU, and no Vulkan device was initialized in this CPU run.

The asynchronous compute unit tests use simulated backends to check immutable input snapshots, CPU-executor verification, fallback, reload rejection, quarantine, and retained snapshot leases. The separate five lifecycle tests exercise pure fence-timeout, late-completion, and close-state policies. They do not call native Vulkan fences or simulate a physical device loss.

## Simulated vanilla world-generation parity

One integration test runs the ordinary vanilla noise-stage fill against delayed CPU-reference slabs completed from a simulated GPU thread. It covers two seeds and coordinates, four X slabs per fixture, and a 128-block vertical extent. It checks that blocks remain untouched until the CPU continuation runs, then compares every block state, both world-generation heightmaps, and post-processing fluid marks with the ordinary vanilla fill. It also exercises a missing slab and confirms cleanup of the active slab.

This is a CPU-reference continuation test, not a GPU result test. Its fixtures use a fixed plains biome, empty structures, and the noise stage only; it does not cover decorated or saved worlds.

## Physical-GPU checks and production-performance limits

Standalone workload-4 exact parity runs completed on two physical FP64 Vulkan devices: an NVIDIA GeForce RTX 3070 (UUID `543d97381f7f3348a4b0b255385e36f0`) and a GeForce GTX 1080 (UUID `eefb282294d5f89200f4c2f5f582b223`). Each device produced 100 exact GPU results for each of six input sizes, 600 results per device, with zero CPU fallbacks, timeouts, rejected jobs, or failed jobs. Every returned result was checked against the exact CPU wire reference.

The measured API latency from request submission through future completion was:

Each size used 16 warmup requests and 100 measured requests in waves of up to four. Latencies include the Java API call, queueing, native dispatch, and result completion; exact comparison ran after the timed interval. The CPU wire-reference figure was one standalone calculation per size, timed once before warmup. It is a single sample, not a repeated CPU latency distribution or a vanilla chunk-generation baseline. The measurements describe this dispatch API and these two devices; they do not show end-to-end terrain speedup. The [portable validation evidence](results/1.1.0-luna-validation.json) records the device-specific runs.

The native async workload-4 suite also completed on both devices. In direct-mapped and staging-buffer modes, each device completed nine native jobs per mode (36 total); each mode included the eight-case startup corpus and a 64 KiB output. The tests verified that submitted inputs were copied before asynchronous use, and all returned outputs matched the exact CPU reference. There were no rejected, timed-out, or failed jobs. A strict mixed-device run accepted and exactly checked 17 RTX 3070 and 16 GTX 1080 results (33 total), with no fallback, rejection, timeout, or failure.

The concurrent legacy workload-1/2 check submitted 160 requests: 114 produced GPU results and 46 used CPU fallback. The set included 32 sequential and 128 concurrent requests. The exact split depends on scheduling and admission pressure; both selected devices produced results for both workloads. A close-pending check completed four native jobs while verifier callbacks were held, closed the service, and confirmed that all four futures returned null. This checks the close ownership path; it does not inject a native Vulkan fence timeout or device loss.

The hardware checks explicitly force GPU dispatch for parity coverage. The mixed terrain check uses `strict` mode and verifies every result on the CPU. These are diagnostic settings; the zero-fallback terrain result is not a promise about admission or performance under normal server settings.

The opt-in physical-device suite can be reproduced with:

```powershell
.\gradlew.bat -I benchmarks/gpu-parity.init.gradle :purpur-server:test --tests org.gpur.GPurRuntimeTestSuite -PgpurGpuTests=true --no-configuration-cache
```

The command above enables the four `VulkanParityTest` hardware tests and the opt-in native async hardware check; the two `AntiXrayParityTest` cases use CPU mocks and are not physical-GPU tests. No live-server load test, soak test, or production TPS comparison has been run for this 1.1.0 artifact.
