# GPur 1.1.0 検証記録

[日本語](1.1.0-validation.md) | [English](1.1.0-validation.en.md)

**状況: 2026-10-09 · Minecraft 26.2 · GPur SNAPSHOT1.1.0**

実行担当と独立監査担当にはGPT-6 luna・xhighを使用しました。環境はWindows 11 Pro（build 26200）、Intel Core i9-11900KF（8コア / 16スレッド）、RAM約96 GiB、OpenJDK 25.0.2、NVIDIA driver 581.57で、両GPUのVRAMは8 GiBです。バックグラウンドのアプリや電源状態は統制していないため、この短時間の実行は性能比較のための隔離実験ではありません。

この記録では、CPU上のコード検証、模擬したワールド生成の同一性検査、実機GPUでの単独検査、本番性能の根拠を分けて示します。最終CPU suiteと実機検査の結果を以下に示します。本番TPSやサーバー処理量の向上は立証していません。

## 成果物とソース

固定したサーバー成果物は`gpur-server/build/libs/gpur-server-26.2-SNAPSHOT1.1.0.jar`です（92,066,088 bytes、SHA-256 `7bdeb2afcb985c03c5f793ff049d76977720c5755836c42dced574c26641c8b7`）。検証対象の実装は`ver/26.2`のソースrevision `f7ec32f2b65c0d86010058552fd6f011d5cd854a`に対応します。最終CPU実行と実機検査の集計を含む持ち運び可能な検証証跡は[1.1.0検証JSON](results/1.1.0-luna-validation.json)にあります。[非同期コード検証記録](results/1.1.0-async-code-validation.json)は先行するコード監査と初回CPU実行を記録しています。

## 記録済みのCPU検証

最終default実行環境はOpenJDK 25.0.2です。パッチ適用とビルドは成功しました。Gradleの試験結果XML 142件を集計し、9,380 tests、failure 0件、error 0件、skip 28件でした。opt-in GPU試験は設定どおりskipされました。配布FP64 shaderはCPU上でSPIR-Vへコンパイルしましたが、このCPU実行ではVulkan deviceを初期化していません。

非同期computeのunit testは模擬backendを使い、入力snapshotの不変性、CPU executor上の照合、CPU fallback、reload後の古い結果の拒否、device隔離、結果保持中のsnapshot leaseを確認します。別のlifecycle test 5件は、fence timeout、遅れて届く完了、close状態の純粋な状態遷移を検査します。native Vulkan fenceを呼び出したり、実機のdevice lossを再現したりする試験ではありません。

## 模擬vanillaワールド生成の同一性検査

統合test 1件では、通常のvanilla noise-stage fillを実行し、模擬GPU threadから遅れて届くCPU参照slabを使って再開します。2つのseed・座標、fixtureごとに4つのX slab、垂直範囲128 blockを対象にしました。CPU continuationが動く前にblockが変更されないことを確かめ、その後、全block state、2種類のworld-generation heightmap、post-processing用fluid markを通常のvanilla fillと比較します。slab欠落時のCPU fallbackと、active slabのcleanupも確認します。

これはCPU参照値を使うcontinuation testであり、GPU計算結果の試験ではありません。fixtureは固定plains biome、空のstructure、noise stageに限定され、decorated worldや保存済みworldを対象にしていません。

## 実機GPU検査と本番性能の限界

workload-4の単独exact GPU parityを、実機のFP64対応Vulkan device 2台で確認しました。NVIDIA GeForce RTX 3070（UUID `543d97381f7f3348a4b0b255385e36f0`）とGeForce GTX 1080（UUID `eefb282294d5f89200f4c2f5f582b223`）で、6種類の入力サイズごとにGPU結果100件、各device計600件を得ました。CPU fallback、timeout、受付拒否、失敗はいずれも0件で、返却された各結果を厳密なCPU wire referenceと照合しました。

| 4K | 1.507 / 2.486 / 2.596 | 1.590 / 3.122 / 3.960 |

各サイズは16件のwarmup後に100件を測定し、最大4件ずつ送信しました。latencyにはJava API呼び出し、queue待ち、native dispatch、結果の完了までを含み、厳密な比較処理は測定後に行います。CPU wire referenceは各サイズで単独計算を1回だけwarmup前に計時しました。これは単発値で、反復CPU latency分布やvanilla chunk-generationの基準値ではありません。この測定が示すのは2台のdevice上のdispatch API動作であり、地形生成全体の高速化ではありません。[持ち運び可能な検証証跡](results/1.1.0-luna-validation.json)にdeviceごとの記録があります。

native async workload-4 suiteも両deviceで完了しました。direct-mappedとstaging-bufferの各modeで、各deviceがnative jobを9件ずつ完了しました（計36件）。各modeで8件のstartup corpusと64 KiBの出力を検査しました。非同期処理へ渡す前に入力がコピーされることを確認し、返却された出力はすべて厳密なCPU referenceと一致しました。受付拒否、timeout、失敗はありませんでした。strict混在device実行ではRTX 3070が17件、GTX 1080が16件、計33件を受け付けて厳密比較し、fallback、受付拒否、timeout、失敗はありませんでした。

workload-1/2の並行検査では160件を要求し、114件でGPU結果、46件でCPU fallbackとなりました。内訳は逐次32件、並行128件です。厳密な件数の分割はschedulerの順序や受付状況で変動します。どちらのdeviceでも両workloadの結果を得ました。close-pending検査では、verifier callbackを保留したままnative job 4件の完了を確認してserviceをcloseし、4件すべてのfutureがnullを返すことを確認しました。これはclose時の所有権処理を検査するもので、native Vulkan fence timeoutやdevice lossを発生させる試験ではありません。

実機検査では、結果一致を確認するためGPUへの処理投入を明示的に強制しています。地形補間の混在検査は`strict`モードで、毎回CPUでも照合しました。これは検査用の設定です。地形検査でfallbackが0件だったことは、通常のサーバー設定での受付率や性能を保証しません。

実機を使うopt-in suiteは次のコマンドで再実行できます。

```powershell
.\gradlew.bat -I benchmarks/gpu-parity.init.gradle :purpur-server:test --tests org.gpur.GPurRuntimeTestSuite -PgpurGpuTests=true --no-configuration-cache
```

このコマンドで有効になる`VulkanParityTest`の4件とopt-in native async hardware checkは実機検査です。`AntiXrayParityTest`の2件はCPU mockを使うため、実機GPU検査には含めません。この1.1.0成果物ではlive server負荷試験、soak test、本番TPSとの比較を実施していません。過去の1.0.0測定は当時記録されたbuildと負荷条件の結果であり、1.1.0の実機対応や性能を立証しません。以前の測定は[実機・負荷検証記録](26.2-validation.md)、実装範囲と制御設定は[非同期地形処理ガイド](26.2-async-terrain.md)を参照してください。
