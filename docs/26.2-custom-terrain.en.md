# GPur 26.2 Custom Terrain (Retired Design)

[English](26.2-custom-terrain.en.md) | [日本語](26.2-custom-terrain.md)

> **Obsolete for the current 1.1.0 implementation.** This archive preserves the earlier custom block-palette terrain design and its implementation notes; the following setup and configuration details are historical and must not be used for new worlds. New unmarked-world selections of `gpur:terrain-v1` are retired and fail at startup. Existing worlds with `gpur-terrain.properties` keep their legacy custom terrain rules on CPU so newly generated chunks remain consistent. Do not delete or edit a world directory or marker. See the [current vanilla terrain interpolation guide](26.2-vanilla-terrain.en.md).

The sections below document the retired implementation as it existed before the opt-in was removed. They are retained for historical reference, not as instructions for the current 1.1.0 code. They do not report new hardware testing or performance validation.

The 1.1.0 server artifact is `gpur-server/build/libs/gpur-server-26.2-SNAPSHOT1.1.0.jar`.

## Opt in a new world

The `worlds` entry associates a generator with that exact world name; it does not create the world or convert an existing one. Your current main world continues to use vanilla CPU terrain. Adding a generator entry for its name cannot convert its existing chunks. Keep the existing world directory intact and choose a new, unused name.

To make a new world the server's main world, set `server.properties` to a new name:

```properties
level-name=gpur_world
```

Then add the matching `worlds.gpur_world` entry to `bukkit.yml` before starting the server:

```yaml
worlds:
  gpur_world:
    generator: gpur:terrain-v1
```

Alternatively, configure the matching `worlds.<name>.generator` entry and have a world-management plugin create that new NORMAL world without supplying a different generator. The plugin-name generator resolver used by `WorldCreator.generator(String)` does not resolve this built-in generator ID directly. Do not use the setting to try to convert an existing world.

The world must use the NORMAL environment, and `chunk-generation.custom-terrain.enabled` must be `true`. This setting enables new opt-ins, but does not select any world by itself. GPur rejects first-time opt-in when it finds existing `.mca` or `.mcc` chunk data. An existing unmarked world is never switched automatically. Nether and End worlds continue to use their existing CPU generators; explicitly selecting `gpur:terrain-v1` for those environments is rejected.

On first world-info validation, GPur atomically writes `gpur-terrain.properties` before generating chunks. The marker stores schema and terrain-rule versions, seed, minimum Y, height, and sea level. Those values are permanent for the marked world. Later loads reject changed seed or height settings, malformed or unsupported markers, and a conflicting generator entry. If you remove the generator entry from `bukkit.yml`, GPur finds the marker and restores the custom generator. Do not delete or edit the marker to turn off GPU compute or regenerate a seed: the marker preserves the world's terrain contract. A marked world still uses the same custom CPU rules when GPU compute is disabled, unavailable, times out, or fails parity.

## GPU readiness and settings

World selection, custom-terrain enablement, and GPU readiness are separate. The world entry opts in to custom terrain. `chunk-generation.custom-terrain.enabled` permits new opt-ins and the terrain scheduler. GPU execution also requires global GPU acceleration and the legacy `chunk-generation.gpu-acceleration.terrain-enabled` gate. Despite its old name, `terrain-enabled` gates GPU compute for the opt-in custom generator; it does not send vanilla terrain generation to a GPU. Disabling either GPU gate leaves marked worlds on the same custom CPU rules.

These are the custom-terrain defaults and related GPU settings:

```yaml
gpu:
  cache:
    enabled: true
  multi-gpu:
    enabled: true
    devices: [auto]
chunk-generation:
  gpu-acceleration:
    enabled: true
    terrain-enabled: true
  custom-terrain:
    enabled: true
    auto-tune: true
    max-batch-chunks: 8
    queue-capacity: 128
    batch-wait-ms: 2
    request-timeout-ms: 250
    parity-interval: 128
```

`gpu.multi-gpu.devices` accepts `auto`, a GPU UUID from startup output, or an exact device name. To select only a GTX 1080, use its exact startup name and disable multiple-device selection:

```yaml
gpu:
  multi-gpu:
    enabled: false
    devices: [NVIDIA GeForce GTX 1080]
```

A configured device may still be unavailable or fail admission; in that case terrain generation uses the CPU reference rules. A GPU being configured does not mean terrain work is running. Work is submitted only when a new chunk is generated in a world that selected `gpur:terrain-v1`, so low GPU use is normal when little custom terrain is being generated.

With `auto-tune: true`, each admitted GPU chooses a batch size from 1, 2, 4, or 8 chunks, bounded by `max-batch-chunks`. A fresh tuning profile uses at most 16 bounded calibration dispatches per device, with CPU/GPU equality checks; a compatible saved profile is checked again at startup. Terrain results also receive periodic parity checks, with the interval set by `parity-interval` (128 dispatches by default). `gpu.cache.enabled` controls persistent Vulkan pipeline and batch-tuning caches. Cache identity includes the physical GPU, driver, shader, and terrain-rules version; incompatible entries are ignored and rebuilt. This is bounded deterministic calibration, not an AI training model.

The runtime status reports per-GPU counts of chunks in accepted GPU dispatches, fallback reasons, and selected batch size. The global `Custom terrain returned` total counts palettes returned to callers by the terrain scheduler, split between GPU and CPU. Per-GPU accepted-dispatch counts can include chunks whose callers timed out and received a CPU palette. Primary-thread CPU generation bypasses the scheduler and is excluded from these counters. They describe scheduler work, not GPU utilization or a promise of speedup.

## Processing boundary

The GPU kernel computes a deterministic palette for the custom terrain shape, including its surface blocks, water, caves, and lava. The Bukkit adapter materializes that palette into chunk data on the generator callback thread. Biome lookup and base-height queries use the same rules on the CPU. Vanilla structures and decorations, including ores, along with lighting, chunk serialization and saving, Mob AI, redstone, plugin callbacks, and world updates remain CPU work. Saving continues through the existing Paper/Minecraft chunk-save path; this change does not add or claim a save optimization.

The integration uses Bukkit's standard chunk-generator and biome-provider callbacks. It does not establish compatibility with every plugin. No new GPU hardware run or whole-server performance run was done for this feature. The historical 1.0.0 hardware and load records remain accurate for the builds and workloads they measured, but they do not cover the 1.1.0 custom-terrain path. No custom-terrain hardware certification or performance improvement is claimed.

The [historical 1.1.0 code validation record](results/1.1.0-code-validation.json) describes the retired implementation snapshot: it reports a clean patch application and JDK 25 build with 9,334 tests, zero failures/errors, and 26 skipped. The shipped shader compiled to SPIR-V on the CPU. Those tests covered terrain continuity and materials, bounded scheduling and shutdown, permanent world markers, cache validation, tuning profile persistence, and readable counters. That record does not validate the current vanilla interpolation path, GPU execution, or whole-server speed.
