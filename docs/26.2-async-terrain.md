# GPur 26.2 バニラ地形の非同期ディスパッチ

[日本語](26.2-async-terrain.md) | [English](26.2-async-terrain.en.md)

**スナップショット記録: 2026-10-09 · GPur 1.1.0 · Minecraft 26.2**

成果物: `gpur-server/build/libs/gpur-server-26.2-SNAPSHOT1.1.0.jar`

この文書では、バニラ地形ノイズ補間の有界な処理を非同期にスケジュールする仕組みを説明します。実装範囲と設定の記録であり、ベンチマーク結果ではありません。

## 対象範囲と維持される動作

GPU経路の対象は、バニラ地形補間が有効なときのバニラ `NoiseBasedChunkGenerator` クラスそのものです。カスタムgenerator、プラグインgenerator、その他の非ノイズgeneratorは従来どおりCPU経路を使います。非同期送信を無効にした場合も、既存のブロッキング型地形ラッパーを利用できます。

バニラの密度グラフ構築とコーナー密度のサンプリングは引き続きCPUで行います。有界スラブが含むのはコピーされた数値だけです。ノイズグラフ、乱数状態、ワールドオブジェクト、generator状態をスレッド間やGPUへ渡しません。シェーダーはFP64で既存の補間を行い、CPUと同じ演算順を維持します。2つの密度スライスにはスラブ境界で共有されるコーナー値をそのまま保持し、ワーカーのスケジュールによって境界の値を再サンプリングしたり移動したりしません。ノイズのサンプリング、シード、チャンクとスラブの形状、ワールド形式は変更しません。量子化や低精度の経路はなく、ノイズ生成全体をGPUへ移す変更でもありません。

## Futureとノイズステージの引き継ぎ

対象スラブは不変な入力スナップショットを持つfutureとして送信されます。GPU結果を待つ間、Moonriseの `NOISE` ワーカーを解放します。futureが完了すると、そのスラブを既存の `parallelGenExecutor` 上でタスクの現在の優先度により逐次再開します。待機中に行われた優先度の変更も再開に反映されます。逐次再開によって状態を持つ `NoiseChunk` の補間順序を保ち、別チャンクの処理は既存のワーカープールで進められます。デバイスから採用可能な結果が返らない場合は、バニラのCPU処理に戻ります。厳密比較が不一致になったデバイスは隔離します。

Vulkanの1バッチに含めるジョブは最大4件で、実際に空いている実行コンテキスト数がさらに上限になります。デバイスごとのキューには最大32件の待機中ジョブを保持し、このほかに実行コンテキスト上のin-flightジョブが存在します。バッチ形成の待機上限は200マイクロ秒です。入力と出力の合計サイズが65,536バイト以上の場合、このしきい値はdevice-localバッファとmapped stagingバッファを選びます。これより小さいジョブも直接mappedされたバッファでGPU実行できます。staged bufferを確保できない場合は直接mappedバッファにフォールバックします。これはバッファ配置の選択であり、GPUジョブの投入条件ではありません。128 MiBのnative allocation予算はデバイスごとに独立して適用され、mapped stagingを含むGPur所有のnativeバッファを対象とします。デバイス全体のVRAM上限ではありません。デバイスが有効なタイムスタンプビットを公開する場合はGPUタイムスタンプを使います。これらは投入量とメモリーを制限する設定であり、高速化を約束するものではありません。

同じ`gpu.scheduler.buffer-budget-mib`設定（既定値128 MiB）は、別枠のサービス全体CPUスナップショット投入予算にも使われます。準備したスラブの入力スナップショットと予定出力サイズを合算し、結果を保持する間その分を計上します。GPU結果のCPU側leaseはスラブを消費するまで保持され、キャンセルまたはフォールバックで結果を破棄すると予約を解放します。このCPU leaseの解放によってnative bufferの寿命が変わることはありません。CPUスナップショット予算に収まらない場合、バニラは元のCPUスラブを保持してCPUで処理します。デバイスごとのnative予算とサービス全体のCPUスナップショット予算は別々に計算されます。それぞれが128 MiBまで使えるため、合算128 MiBの上限ではありません。どちらもJVMヒープ全体やデバイスVRAM全体の上限ではありません。

複数のFP64デバイスが使える場合、スケジューラーは各デバイスの観測dispatch latency/valueのEWMAとpending workのコストから推定した完了時間が最も短いデバイスを選びます。この推定はスケジューリングのヒントであり、GPU投入可否や計算結果の正しさを決める条件ではありません。

```yaml
gpu:
  scheduler:
    async-submit: true
    batch-max-jobs: 4
    batch-window-us: 200
    queue-capacity: 32
    device-local-threshold-bytes: 65536
    buffer-budget-mib: 128
    timestamps: true
  verification:
    full-first-batches: 16
    sample-one-in: 128
chunk-generation:
  vanilla-terrain:
    enabled: false
    mode: disabled
```

設定キーは`full-first-batches`ですが、数えるのはVulkanのnative batchではなく、個々の地形スラブ／ジョブで成功した完全なCPU比較です。16件の完全比較が成功するまでは完全比較を要求します。比較中にも複数ジョブをdispatchできるため、warmupでは16件を超えるジョブが完全比較されることがあります。

必要なcompute APIはVulkan 1.1のままです。送信したネイティブバッチはVulkan fenceで完了を確認し、ホスト側で状態をポーリングします。GPurはtimeline semaphoreを必要としません。キュー過負荷、デバイス喪失、タイムアウトでは既存のCPU経路へ戻ります。

## 検証モード

バニラ地形のGPU offloadを有効にすると、起動時とドライバーまたはデバイスの再読み込み後に、各デバイスでスタートアップコーパスを実行します。コーパスには有界な形状と浮動小数点の境界値を含めます。コーパスを通過するまで、そのデバイスの地形結果を採用しません。

| モード | CPUとの比較 | GPU結果の採用 |
| --- | --- | --- |
| `disabled` | 地形GPUディスパッチなし | なし |
| `observe` | すべての地形スラブ／ジョブとスタートアップコーパス | なし。バニラCPU結果を維持 |
| `verified-exact` | コーパス、最初の16件の完全比較成功、その後はジョブごとにランダムな128回に1回 | サンプリング方針のもとでFP64の厳密結果を採用可能 |
| `strict` | すべての地形スラブ／ジョブとスタートアップコーパス | CPUとの厳密一致を確認してから採用 |

新規設定の既定値は `disabled` です。`mode`を明示すると`enabled`と`verify-every-batch`より優先されます。たとえば`enabled: false`でも`mode: strict`なら有効になり、`enabled: true`でも`mode: disabled`なら無効です。`mode`を省略した場合は従来設定との互換性を保ち、`enabled: false`は`disabled`、`enabled: true`かつ`verify-every-batch: true`は`strict`、`false`は`verified-exact`になります。後者では従来のパリティ間隔をサンプル間隔として使います。検証設定が変えるのは比較頻度だけで、量子化シェーダーを選ぶことはありません。サンプリングモードでは、その後の全スラブを個別に比較するわけではありません。スラブごとのCPUパリティが必要な場合はstrictモードを使ってください。

デバイスメトリクスのpayload counterは論理ジョブの入力／出力サイズであり、物理PCIe転送量ではありません。submit、host-write、readback、queueなどのCPUフェーズ時間はジョブやコンテキスト間で重なることがあるため、合算してもwall-clock時間にはなりません。利用可能なVulkan timestampが計るのはシェーダー実行時間だけで、queue待ち、転送、fence待ちは含みません。timestamp queryを使えない場合のfence待ち時間はホスト側の完了時間であり、シェーダーだけの時間ではありません。

実機のRTX 3070とGTX 1080でworkload-4の単独dispatchを実行し、各deviceの6入力サイズでCPU参照値との完全一致を確認しました。この実行はcompute APIとnative結果経路を検査しますが、vanilla chunk-generation全体をGPUで動かすものでも、サーバー全体の高速化を示すものでもありません。過去の1.0.0実機・負荷結果は、当時のビルドと負荷条件に限った測定として有効であり、1.1.0の地形スケジューリングを検証するものではありません。

## コード検証

[コード検証記録](results/1.1.0-async-code-validation.json)には、パッチ適用・コンパイル・CPU上のシェーダーコンパイルの成功と、9,379件のテストで失敗・エラー0件、スキップ27件を記載しています。実際のバニラ生成器で遅れて届くCPU参照スラブを再開する試験は模擬結果を使い、タイムアウト、キャンセル、reload、隔離、結果保持予算は状態ポリシーを検査します。別の[1.1.0検証記録](1.1.0-validation.md)に、単独の実機GPU dispatch結果を記載しています。実機でfence timeoutやdevice lossを発生させる試験、GPU結果を使うvanilla生成全体の試験、サーバー性能の向上は立証していません。
