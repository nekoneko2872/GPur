# GPur 26.2 Asynchronous Vanilla Terrain Dispatch

[English](26.2-async-terrain.en.md) | [日本語](26.2-async-terrain.md)

**Snapshot note: 2026-10-09 · GPur 1.1.0 · Minecraft 26.2**

Artifact: `gpur-server/build/libs/gpur-server-26.2-SNAPSHOT1.1.0.jar`

This note describes how bounded vanilla noise interpolation work is scheduled asynchronously. It records implementation scope and controls, not a benchmark result.

## Scope and preserved behavior

The GPU path applies only to the exact vanilla `NoiseBasedChunkGenerator` class when vanilla terrain interpolation is enabled. Custom generators, plugin generators, and other non-noise generator paths continue through their original CPU implementations. When asynchronous submission is disabled, the existing blocking terrain wrapper remains available.

The CPU still builds the vanilla density graph and samples its corner densities. A bounded slab contains copies of those numeric values; it does not carry a noise graph, random state, world objects, or generator state across threads or to the device. The shader performs the existing interpolation in FP64 and preserves the CPU operation order. Both density slices retain the exact shared corner values at slab boundaries; worker scheduling does not resample or shift those seam inputs. Noise sampling, seeds, chunk and slab geometry, and world format are unchanged. There is no quantized or reduced-precision path, and this does not move full noise generation to the GPU.

## Futures and noise-stage handoff

Each eligible slab is submitted as a future backed by an immutable input snapshot. While its GPU result is pending, the Moonrise `NOISE` worker is released. When the future completes, that slab resumes serially on the existing `parallelGenExecutor` at the task's current priority. Priority changes made while the task is suspended are reflected in its resumption priority. Serial resumption preserves the stateful `NoiseChunk` interpolation order; work from different chunks can continue through the existing worker pool. If no device returns an accepted result, vanilla computes the slab on the CPU. An exactness mismatch quarantines the affected device.

Vulkan batches contain up to four jobs, limited further by the actual free execution contexts. A per-device queue holds at most 32 pending jobs, in addition to jobs occupying available in-flight execution contexts. The scheduler waits up to 200 microseconds to form a batch. The 65,536-byte threshold selects device-local buffers with mapped staging when combined input and output size reaches the threshold; smaller jobs can still use the GPU through directly mapped buffers. If staged allocation is unavailable, the device falls back to directly mapped buffers. This is a buffer-placement choice, not a GPU admission threshold. The 128 MiB native allocation budget applies independently to each device and covers GPur-owned native buffers, including mapped staging buffers; it is not a limit on total device VRAM. GPU timestamps are enabled where the device exposes usable timestamp bits. These bounds manage work admission and memory; they do not promise a speedup.

The same `gpu.scheduler.buffer-budget-mib` setting (128 MiB by default) also sets a separate service-wide CPU snapshot admission budget. It charges each prepared slab's input snapshot plus planned output while that result is retained. A successful CPU-result lease remains charged until the slab is consumed; cancellation or fallback releases the reservation when that result is abandoned. Releasing this CPU lease does not change native buffer lifetimes. If the CPU snapshot budget cannot admit a slab, vanilla keeps and computes the original CPU slab. The per-device native budgets and the service-wide CPU snapshot budget use independent accounting: each can reach 128 MiB, so they are not a combined 128 MiB cap. Neither one limits total JVM heap or total device VRAM.

When several FP64 devices are available, the scheduler chooses the device with the lowest estimated completion cost using a per-device EWMA of observed dispatch latency per value plus its pending-work cost. This estimate is a scheduling hint, not an admission or correctness gate.

```yaml
gpu:
  scheduler:
    async-submit: true
    batch-max-jobs: 4
    batch-window-us: 200
    queue-capacity: 32
    device-local-threshold-bytes: 65536
    buffer-budget-mib: 128
    timestamps: true
  verification:
    full-first-batches: 16
    sample-one-in: 128
chunk-generation:
  vanilla-terrain:
    enabled: false
    mode: disabled
```

Despite the configuration key `full-first-batches`, the value counts successful full CPU comparisons of individual terrain slabs/jobs, not native Vulkan batches. The policy keeps requesting full comparisons until 16 successful comparisons complete. Because concurrent jobs may be dispatched while earlier comparisons are still pending, more than 16 jobs can receive a full comparison during warmup.

The compute API requirement remains Vulkan 1.1. Each submitted native batch is completed with a Vulkan fence that the host polls; GPur does not require timeline semaphores. Queue pressure, device loss, and timeouts return work to the existing CPU path.

## Verification modes

The startup corpus is run against each device after initialization and after a driver/device reload whenever vanilla terrain offload is enabled. It covers bounded workload shapes and floating-point edge cases. A device must pass this corpus before its terrain results are accepted.

| Mode | CPU comparison | GPU result adoption |
| --- | --- | --- |
| `disabled` | No terrain GPU dispatch | Never |
| `observe` | Every terrain slab/job, plus the startup corpus | Never; vanilla keeps the CPU result |
| `verified-exact` | Startup corpus, first 16 successful full slab/job comparisons, then a randomized 1-in-128 sample per job | Exact FP64 results may be adopted under the sampled policy |
| `strict` | Every terrain slab/job, plus the startup corpus | Only after exact CPU parity succeeds |

Fresh configuration defaults to `disabled`. An explicit `mode` is authoritative over `enabled` and `verify-every-batch`: for example, `mode: strict` enables the vanilla GPU path even when `enabled: false`, while `mode: disabled` keeps it off even when `enabled: true`. If `mode` is absent, the legacy mapping applies: `enabled: false` maps to `disabled`; `enabled: true` with `verify-every-batch: true` maps to `strict`, and `false` maps to `verified-exact`, using the legacy parity interval as its sample interval. The verification settings control comparison frequency; they never select a quantized kernel. A sampled policy does not compare every later slab individually, so strict mode remains the choice when per-slab CPU parity is required.

Device metrics need interpretation: input/output payload counters are logical job sizes, not physical PCIe traffic. CPU phase counters such as submit, host-write, readback, and queue time can overlap across jobs and contexts, so adding them does not yield wall-clock time. Supported Vulkan timestamps measure shader execution duration only; they exclude queueing, transfers, and fence wait. Where timestamp queries are unavailable, fence-wait timing is a host-side completion measure rather than a shader-only duration.

Standalone workload-4 dispatch runs completed on physical RTX 3070 and GTX 1080 devices, with exact CPU-reference matches across six request sizes on each. These runs exercise the compute API and native result path; they do not run the complete vanilla chunk-generation pipeline or establish whole-server speedup. The previous 1.0.0 hardware and load results remain measurements of their recorded builds and workloads; they do not validate 1.1.0 terrain scheduling.
