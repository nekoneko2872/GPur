# GPur 26.2 Migration and Validation Record

[日本語](26.2-migration.md) | [English](26.2-migration.en.md)

GPur now uses Purpur 26.2 as its base, with a Vulkan compute layer that can load existing GPur settings. Plugins, events, random number generation, and commits of changes to the world run on the CPU.

**Full GPU migration of Mob AI, redstone, and player processing is not implemented. In the earlier test where all 300 players moved simultaneously, conducted before the GPU retry and result acceptance fixes, ticks stalled in every configuration: CPU, RTX 3070, GTX 1080, and mixed GPUs. The final tests also do not establish continuously stable TPS or performance equal to or better than the CPU configuration.** The validation below covers the limited compute paths implemented and samples of compatibility behavior.

## Implementation Scope

| Area | Current processing |
| --- | --- |
| Nearest-player searches and player distances for natural spawning | FP64 coordinate snapshots are sent to the GPU. Operation order, strict range comparisons, and ordering of equal-distance results are preserved. Arbitrary plugin predicates use the CPU path. |
| Anti-Xray | Paper's HIDE mode uses GPU-computed integer masks that account for neighboring blocks in all six directions. The entire packet is written to a separate buffer, and all bytes are periodically compared with the original Paper processing. |
| Anti-Xray random replacement modes and special non-occluding block settings | Original Paper CPU processing. The order in which random numbers are consumed is preserved. |
| Mob AI; player movement, collision, and state updates; dependent redstone updates | Original CPU processing. Event cancellation and changes to values are preserved. |
| Terrain and structure generation | Original CPU processing. The old GPur FP32 interpolation and alternative terrain generation are not used. |
| Elytra preloading | The CPU determines priorities from movement and viewing direction. Nearby chunks take priority, and the default additional loading range is limited to three chunks. Send-distance and simulation-distance settings are preserved. |

Processing falls back to the CPU if the GPU is slow, busy, unsupported, returns a mismatched result, or fails to execute. GPU result acceptance, device disabling, Anti-Xray rejection, and service shutdown are committed within the same short critical section, so results from concurrent requests that return after disabling are not accepted. Results whose acceptance has already been committed are not revoked. GPU execution, CPU reference computation, and waiting for native resource shutdown take place outside the critical section. Buffers used by timed-out operations are not reused by other requests. Vulkan host memory uses a region cached for reads when one is available.

## Configuration Migration

Existing `gpur.yml` files are migrated to schema 2. Custom keys and values are retained. Only schema 1 settings that still match the old defaults are changed as follows:

- `gpu-offload.mob-spawn.min-candidates`: 32 → 1, because no path supplied 32 candidates in a single query.
- `gpu-offload.anti-xray.min-sections`: 12 → 1, resolving the issue where ordinary packets did not meet the threshold.
- Invalid numbers are clamped to their valid ranges and saved. `allow-inexact-results` is disabled to prioritize identical behavior.

The default player-distance search threshold is 128 players. Natural spawning requires at least 32 players and at least 128 distance calculations. Small queries use the CPU because transfer costs are high. These settings are not intended to keep the GPU continuously active.

```yaml
gpu:
  multi-gpu:
    enabled: true
    devices: [auto]
  force: false
  timeout-ms: 100
```

`devices` accepts UUIDs shown in the startup log, exact GPU names, or `auto`. Mixed GPUs are treated as independent Vulkan devices and do not require SLI or NVLink. With `enabled: false`, the first device that passes validation is used.

`force: true` is for diagnostics and removes the preference for the CPU based on speed. It does not disable result equality checks or safety limits. In normal operation, if dispatch and readback are slower than CPU computation, the affected computation falls back to the CPU for 30 seconds. Every retry after that interval is compared with a CPU reference computation; if it is still slower, it waits another 30 seconds. CAS updates prevent an older concurrent comparison result from clearing a newer waiting deadline. This comparison does not include server-wide costs such as preparing snapshots.

Old settings for terrain, structures, reload retention, throughput stabilization, and send bursts are retained for migration, but their old paths are not executed. `gpu-usage-fallback` refers to execution-context occupancy, not GPU hardware utilization. GPur does not automatically enable Anti-Xray in worlds where Paper's Anti-Xray is disabled.

Paper, Purpur, and plugin configuration file formats and API packages are preserved. Production settings and worlds have not been copied into this development checkout.

## Validation

Environment: Windows 11, JDK 25.0.2, and LWJGL 3.4.1.

| GPU | Validation |
| --- | --- |
| NVIDIA GeForce RTX 3070 | FP64 boundaries, Anti-Xray integer masks, concurrent requests, single-GPU and mixed-GPU configurations |
| NVIDIA GeForce GTX 1080 | Same as above |

Vulkan 1.1, a compute queue, `shaderFloat64`, and host-visible coherent memory are required. The lowest GPU tested on physical hardware was the GTX 1080. Older GPUs are not guaranteed as the minimum supported model. Each device undergoes result equality checks at startup.

There are 38 GPur-specific JUnit tests. They cover configuration migration, preloading, numerical boundaries, brand compatibility, Anti-Xray local and global palettes, three dimensions, neighboring chunks and missing sections, recovery from invalid GPU results, retry backoff, races between result acceptance and disabling, waypoint iteration order, and physical GPUs. Anti-Xray tests compare every byte in 48 packets. The four GPU tests run only when explicitly enabled.

`gradlew build`, as used in GitHub CI, also passed. JUnit reports across all modules recorded 9,831 tests, zero failures or errors, and 28 skips. The four GPU tests are skipped in this normal build; all 38 GPur-specific JUnit tests, including physical GPU checks, passed in a separate explicit run. The build also includes API Checkstyle, Javadoc, and forbidden-call checks.

After moving the source folders to `gpur-*`, the full build and physical GPU checks were rerun. All passed with the same test counts. See the [post-move check record](results/relocated-build-checks.json).

The distributable Paperclip JAR was started in isolated CPU and RTX 3070 + GTX 1080 configurations. Loading old settings, `gpur status`, `gpur reload`, `version`, and clean shutdown were checked. A normal Bukkit plugin compiled with Java 21 verified CPU-thread execution of lifecycle callbacks, scheduler tasks, and events, cancellation of Mob spawn events, and changing redstone power to 7 through an event. These tests do not prove compatibility with every plugin.

Separate tests used 300 real TCP-connected players, 3,000 AI Mobs, 300 redstone circuits, and fresh chunk generation in CPU, RTX 3070, GTX 1080, and mixed-GPU configurations. Every tick, client counts and errors, CPU and memory usage, GC, and GPU operation counts were recorded. See the [load validation record](26.2-validation.en.md) for details and the failed all-player movement test. No control test against standard Paper or Purpur was conducted, so these results do not demonstrate a whole-server speedup.

For waypoint tables used during player movement, snapshots now use `List.copyOf` while preserving the same iteration order, removing unnecessary entry hashing. Tests were added for removing and replacing entries during row and column iteration. This has not resolved the packet-processing backlog caused by continuous movement by all 300 players.

## Reproduction

Use JDK 25 and run each command separately in a Git checkout.

```powershell
$env:JAVA_HOME = 'C:\Path\To\jdk-25'
.\gradlew.bat applyAllPatches --console=plain
.\gradlew.bat :purpur-server:test --rerun --tests 'org.gpur.GPurRuntimeTestSuite' --tests 'org.gpur.preload.GPurPreloadTestSuite' -PgpurGpuTests=true :purpur-server:createPaperclipJar --console=plain
.\gradlew.bat build --console=plain
```

Omit `-PgpurGpuTests=true` in environments without a GPU. When changing generated Minecraft or Paper sources, finish `fixupMinecraftSourcePatches` and `fixupPaperServerFilePatches`, then run `rebuildAllServerPatches` in a separate Gradle invocation. Patch application and the build should also be separate invocations.

Source folders have been moved to `gpur-server`, `gpur-api`, and `gpur-checkstyle`. Gradle project names such as `:purpur-server` remain unchanged, so the commands above continue to work. Public API package names are also preserved.

Launch JAR: `gpur-server/build/libs/gpur-server-26.2-SNAPSHOT1.0.0.jar`. The distribution name combines `mcVersion` (26.2) and `gpurVersion` (SNAPSHOT1.0.0) from `gradle.properties`. The public API version remains unchanged. `-dev.jar` is for development, and `gpur-bundler-*.jar` is a build intermediate. Launch with JDK 25 and `--enable-native-access=ALL-UNNAMED`.

## Git and Distribution

The new local branch is `ver/26.2`. Upstream commit history, README contributor and sponsor lists, donation links, IDE settings, unapplied old-version patches, the unused upstream test plugin, and the Purpur logo replacement patch were excluded from the new branch's history. Required copyright, license, and patch attribution notices are retained.

Generated sources, raw validation logs, test worlds, runtime settings, and JARs are excluded from Git. Validation summaries, reproduction tools, and the Gradle wrapper JAR required for the build are included. The code is maintained on `ver/26.2`, independently of the existing branches.
