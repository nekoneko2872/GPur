# Runtime diagnostics and elytra preloading

[English](26.2-runtime-updates.en.md) | [日本語](26.2-runtime-updates.md)

This update makes `/gpur status` readable and reduces unnecessary directional preload work. It does not add GPU terrain generation. The [large-load validation](26.2-validation.en.md) remains a historical measurement of its recorded build.

## Status display

The default command groups named calculations under each GPU. It distinguishes unavailable devices, configuration-disabled calculations, no results yet, GPU enabled, CPU cooldown with a retry countdown, and blocked Anti-Xray processing. Colors accompany text labels. Available/idle does not mean actively computing. Terrain generation and directional chunk priority are explicitly labeled CPU.

`/gpur status detail` adds millisecond timings, CPU reference samples, cooldown history, UUIDs, and admission skips. Hover explanations describe the counters; the detail link runs the command. The compact mixed-device example occupies 16 lines with a maximum of 46 characters per line.

Result counts mean accepted GPU batches since startup/reload, not players, ticks, or final packet applications. CPU fallbacks cover submitted attempts only; admission skips also exclude many earlier CPU paths. Neither measures all CPU work. In-flight jobs are occupied execution contexts, not GPU utilization. Force mode bypasses performance cooldown, but safety and Anti-Xray rejection remain enforced.

## Preload changes

- New configurations keep directional priority enabled, with `max-extra-distance: 0` and `elytra-throughput-boost.enabled: false`. Existing explicit values are retained.
- Extra radius enlarges loading/generation in every direction; the flight boost could double CPU generation requests. Directional priority does not need either increase.
- Priority bands are cached while geometry and the queue center remain fixed. The cache is cleared after affected queues are emptied, before a rebuild.
- Lookahead changes beyond the entire queue no longer trigger a rebuild. Flight speed is updated independently for explicitly enabled rate boosts.
- Inactive directional preloading uses Paper's original comparator.

The legacy `terrain-enabled` setting does not implement GPU terrain generation. One connected player normally does not satisfy distance-offload thresholds. Anti-Xray GPU work can occur, then temporarily prefer CPU when sampled dispatch is slower.

## Validation

All 240 Minecraft file patches and 42 Paper file patches applied. The server test task completed **9,311 tests, 0 failures, 0 errors, 27 skipped**. Runtime checks compared cached/uncached priority at 8,978 positions, verified inactive Paper ordering, exercised compact/detailed/rejected/forced/stopped displays, received hover metadata through a real TCP client, and reloaded both GPUs. The standalone benchmark classpath helper was corrected and run successfully.

The flight experiment used a test-only plugin and one real loopback TCP client, fresh normal-terrain worlds with seed 4729262, view/simulation distance 10, a 16 GiB heap, four chunk workers, and RTX 3070 + GTX 1080 with adaptive GPU settings. The fixture advanced a gliding server player by 1.6 blocks per tick for 600 ticks. This is a **synthetic server-driven trace**, not a complete simulation of elytra controls or fireworks. Builds finished before measurement. The user's other plugins were not included.

| Metric | Old JAR + old settings | Updated JAR + priority-only settings |
| --- | ---: | ---: |
| Mean MSPT | 8.67 | 9.19 |
| p95 MSPT | 21.50 | 25.31 |
| p99 MSPT | 37.74 | 32.93 |
| Maximum MSPT | 85.02 | 46.08 |
| Ticks over 50 ms | 1 | 0 |
| Wall-time tick rate | 19.994 | 19.999 |
| Load radius during flight | 14 | 11 |

Both runs completed with all 600 flight samples active and no client errors. The updated run recorded 262 accepted GPU Anti-Xray batches across startup, settling, and flight; player-distance GPU results remained zero. Both Anti-Xray workloads were in CPU cooldown when status was read. GPU processing occurred, but most server work remained CPU processing.

This single pair improved maximum and p99 while mean and p95 were worse. It does **not** establish overall speedup, CPU-equivalent performance across configurations, or a guarantee against future TPS drops. Code and settings changed together, so their individual effects are not isolated. An earlier fixture attempt recorded 601 samples and was excluded. No new 300-player/3,000-Mob matrix was run for this update.
