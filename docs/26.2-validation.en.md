# GPur 26.2 Load Validation

[日本語](26.2-validation.md) | [English](26.2-validation.en.md)

> Historical record: the hardware and load tables below cover the earlier 1.0.0 build and its recorded workloads. They remain unchanged and do not validate GPur 1.1.0. See the [1.1.0 validation record](1.1.0-validation.en.md) for current evidence and limits.

The CPU-only, RTX 3070, GTX 1080, and mixed-GPU configurations were measured under the same conditions after fixing concurrent GPU result acceptance and device disabling. With 300 connected players and 60 moving at 20 Hz, the fixed 3,000-AI-mob phase recorded 4.14 TPS and 129 ticks above 50 ms on the CPU configuration. The full results for each condition appear below. Sustained 20 TPS and zero tick drops were not achieved. There is also no control test against standard Paper/Purpur, so a whole-server speedup has not been demonstrated.

The final completion criterion was relaxed to performance equivalent to or better than the CPU configuration. However, these short measurements, with one run per configuration, show improvements in TPS, p50, and p95 on the 3070, lower TPS than the CPU in the fixed-AI phase on the 1080, and worse p95 and p99 in the mixed configuration. Normal variation in natural spawning, AI, and GC is included, so these differences cannot be attributed conclusively to the GPU. Equivalent-or-better performance across all configurations has not been demonstrated either. The absolute number of ticks above 50 ms varies with the number of completed ticks; that count alone is not evidence of a performance difference.

## GPU Dispatch and Host Resources

`GPU results` are GPur's per-device/per-workload cumulative totals at the end of each run. Workload 1 is FP64 nearest-distance calculation; workload 2 is Paper HIDE Anti-Xray integer masks. Dispatch counts demonstrate that GPU computation ran. They do not mean that every query or every tick was processed by the GPU. Slow dispatches are reevaluated after a 30-second backoff. Plugins, mob AI, player state updates, events, random numbers, terrain generation, and redstone updates remain on the CPU.

## CPU Load Diagnosis

In the locally saved spark samples covering the full runs, `Entity.setPos` accounted for 32.75–33.85% of Server thread samples across the configurations, and `runAllTasksAtTickStart` for 20.31–21.38%. In the CPU configuration, `ServerWaypointManager.updateConnection` also accounted for 17.04%. These are inclusive times that overlap with one another and include setup such as placement, as well as waiting. Do not add the percentages or use them as a breakdown of only the fixed-AI phase. The [extracted profiles](results/profiles.json) retain the top methods for each configuration.

## Pre-Backoff Diagnosis with All Players Moving

Four runs with all 300 players moving at 20 Hz—CPU (`20261007-025406-748100-cpu`), RTX 3070 (`20261007-025921-286200-rtx3070`), GTX 1080 (`20261007-030345-862300-gtx1080`), and mixed (`20261007-030807-557500-mixed`)—ended with watchdog exit code 70 after ticks stalled for approximately 60 seconds. These runs already used the version with both `ServerWaypointManager` snapshots changed to `List.copyOf`; that CPU optimization alone did not prevent the stall. Failure stacks showed `updatePlayer`/`updateWaypoint`, Guava table entry/column traversal, `Entity.setPos`, and movement packet processing. These diagnostic runs preceded the backoff/result-acceptance fixes and must not be combined with the final 20%-walking matrix. A stalled tick has no TickEnd sample, so the last MSPT value cannot be treated as the stall duration.

CPU usage of 100% represents one logical CPU; the client fleet also ran on the same host. The synthetic travel command runs for 100 simulation ticks, and its phase CSV contains 100–101 records including boundary ticks.

Each case is a single short measurement on the same host and seed. These runs do not establish statistical significance of the differences, generalization to other hardware/plugins/worlds, capacity for all 300 players to keep moving, or a future zero-drop guarantee. There is no standard Paper/Purpur control test, and migration of all mob AI or all player processing to the GPU is not implemented. Read these results as a record of this limited workload and execution environment.
