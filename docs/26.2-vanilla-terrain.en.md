# GPur 26.2 Vanilla Terrain Noise Interpolation

[English](26.2-vanilla-terrain.en.md) | [日本語](26.2-vanilla-terrain.md)

GPur 1.1.0 contains an opt-in, bounded Vulkan path for the interpolation stage of the existing vanilla terrain generator. It is disabled by default. This page describes code scope and settings; the [1.1.0 validation record](1.1.0-validation.en.md) reports standalone physical-device checks and their limits.

The 1.1.0 server artifact is `gpur-server/build/libs/gpur-server-26.2-SNAPSHOT1.1.0.jar`.

The [asynchronous dispatch guide](26.2-async-terrain.en.md) covers the newer executor, batching, timestamps, and verification modes. An explicit `chunk-generation.vanilla-terrain.mode` overrides the legacy `enabled` and `verify-every-batch` settings below.

## What runs on the GPU

The normal Paper/Purpur vanilla generator remains selected. No `bukkit.yml` generator entry or new world is needed, and existing world directories, saved chunks, seeds, datapacks, and save format are not replaced. Turning this option on keeps the vanilla generation rules and applies the GPU path only to bounded noise-density interpolation work.

The CPU builds the vanilla density graph and computes the actual corner densities. A GPU can interpolate those values across a bounded slab using FP64 and the CPU operation order. With strict verification enabled, each GPU batch is compared against the complete CPU reference for that slab. The GPU does not generate whole chunks.

The CPU retains density/noise graph construction, random-number generation, blending, aquifers, surface rules, caves, biomes, structures, block placement, lighting, chunk serialization, and saving. Decoration, structures, and world changes continue through the ordinary Paper/Purpur paths. The work still depends on the existing world-generation workload; this release makes no throughput or range guarantee.

## Configuration

The option defaults to `false`. GPU use also requires both the global GPU-acceleration gate and the existing terrain gate. Use the normal device selectors in `gpu.multi-gpu.devices` to choose the device or devices.

```yaml
gpu:
  multi-gpu:
    enabled: true
    devices: [auto]
chunk-generation:
  gpu-acceleration:
    enabled: true
    terrain-enabled: true
  vanilla-terrain:
    enabled: false
    verify-every-batch: true
    max-interpolators: 16
    max-slab-values: 1048576
    minimum-values: 1024
    parity-interval: 128
```

If no explicit `mode` is present, set `chunk-generation.vanilla-terrain.enabled: true` to opt into the vanilla interpolation path. It does not select a generator or change world creation. `max-interpolators` and `max-slab-values` bound admitted work; slabs smaller than 1,024 values stay on the CPU. The legacy `verify-every-batch: true` selects strict comparison of every slab. With that setting false, the legacy `parity-interval` supplies the randomized sample interval unless `gpu.verification.sample-one-in` is explicitly set. Keep strict verification for individual result checks; sampled verification trades those later checks for lower CPU work and does not validate every adopted result. This path has not been performance-validated, and `gpu.force: true` is not a performance recommendation.

Device selectors accept `auto`, a UUID shown at startup, or an exact device name. For example, this selects only the GTX 1080 by its displayed name; selection alone does not certify performance for this terrain path:

```yaml
gpu:
  multi-gpu:
    enabled: false
    devices: [NVIDIA GeForce GTX 1080]
```

Device availability, successful parity, and workload size determine whether GPU work is accepted. A configured or idle GPU does not mean that terrain work is being dispatched, and device occupancy is not hardware utilization. Use startup logs and `/gpur status` to check runtime readiness and the available workload counters.

## Preloading is a separate CPU workload control

`chunk-generation.preloading.max-extra-distance` defaults to `0`. Setting it to `2` expands the existing preload range in all directions and can increase CPU chunk loading, generation, and sending work. It does not enable GPU interpolation or change vanilla terrain rules.

On a high-spec server, the elytra concurrency boost is an optional CPU-workload control:

```yaml
chunk-generation:
  preloading:
    max-extra-distance: 2
    elytra-throughput-boost:
      enabled: true
      max-extra-concurrent-generates: 8
      concurrent-generates-multiplier: 2.0
```

The boost defaults to disabled and only applies while a player is actively flying with an elytra. With the multiplier at its default `2.0`, GPur adds at most `max-extra-concurrent-generates` concurrent generation slots above Paper's resolved automatic or explicit baseline: `min(ceil(baseline × (multiplier − 1)), max-extra-concurrent-generates)`. The addition saturates at the integer maximum; Paper's `-1` unlimited sentinel is preserved. The cap defaults to `8` and accepts `0..64`. This concurrency allowance is separate from the `generate-rate-multiplier`, which changes generation request rate. The concurrency setting does not select more distant chunks; `max-extra-distance` does. Enabling either option can increase CPU work and does not guarantee TPS. Neither option changes vanilla terrain rules or enables GPU interpolation.

## Retired custom generator

New unmarked-world selections of `gpur:terrain-v1` are retired and fail with an actionable startup error. Remove that generator entry to use vanilla terrain, or set `server.properties` `level-name` to the intended existing vanilla world directory. For example, to load the existing world directory named `gpur`, set:

```properties
level-name=gpur
```

Remove a matching `worlds.gpur.generator` entry from `bukkit.yml` if one is present. Keep every world directory and marker file intact. A world containing `gpur-terrain.properties` is a marked legacy custom-terrain world; GPur restores its legacy custom generator and keeps using the same custom CPU rules even when GPU terrain is disabled. Do not delete or edit that marker to convert the world.

The old `chunk-generation.custom-terrain.enabled` setting does not select a world or enable the vanilla interpolation path. Use `chunk-generation.vanilla-terrain.enabled` for the bounded vanilla path described here.

## Validation scope

The historical 1.0.0 hardware and load records remain valid for the builds and workloads they measured, but they do not measure the 1.1.0 vanilla noise-interpolation path. Two physical devices have completed standalone workload-4 exact-dispatch checks, as described in the [1.1.0 validation record](1.1.0-validation.en.md). These API-level checks are not complete vanilla-world generation, hardware certification, or a performance claim; the GPU path remains experimental and bounded.

The [code validation record](results/1.1.0-vanilla-code-validation.json) reports successful patch application and builds, with 9,346 tests, zero failures or errors, and 26 skipped tests. CPU-reference slabs were injected into the real vanilla `NoiseChunk` to compare density bits, block states, aquifer fluid-update flags, and cleanup at negative coordinates and near the world border. That run did not test GPU hardware results or compare complete decorated and saved worlds; the later standalone GPU checks are summarized in the [1.1.0 validation record](1.1.0-validation.en.md).
