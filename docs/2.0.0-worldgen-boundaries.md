# 2.0.0 worldgen boundaries: source audit

This is a source-level design audit of the current generated Minecraft code and GPur kernels. It does not claim a full GPU density graph, aquifer, or chunk-generation implementation. The present GPU boundaries are workload 5 (exact noise leaf samples), workload 4 (terrain interpolation), and workload 6 (aquifer-center ranking). In particular, workload 6 returns four candidate indices; `NoiseBasedAquifer.computeSubstance` still recomputes their distances and runs the original fluid/status/pressure logic on the CPU.

## Runtime order and current boundary

`NoiseChunk` first maps the router with `wrap`, creates `fullNoiseDensity` as `cacheAllInCell(add(wrappedRouter.finalDensity(), beardifier))`, and puts `aquifer.computeSubstance(context, fullNoiseDensity.compute(context))` first in its `MaterialRuleList`. Ore-vein classification follows when enabled. This makes the actual sequence: build corner noise slices; interpolate the slice values; evaluate the final density graph; ask the aquifer for a state; optionally run ore-vein rules; then commit the resulting block and update heightmaps/post-processing. See `NoiseChunk` constructor, `fillSlice`, `selectCellYZ`, `NoiseInterpolator`, and `NoiseBasedChunkGenerator.doFill` / `gpurFillFromNoiseAsync`.

The current static-noise collector visits interpolator fillers and snapshots only initialized `NormalNoise`/`BlendedNoise` profiles and static coordinates. Its exact sampler-identity plus raw-coordinate-bits cache is scoped around `fillSlice`; a miss runs the original CPU graph. Its `mapChildren` walk ignores reconstructed return nodes and never calls `NoiseChunk.wrap`, so discovery does not install or mutate runtime wrappers. Do not turn that discovery visitor into a replacement visitor: `wrap` registers mutable interpolation and cache wrappers. Workload 4 preserves two distinct `NoiseInterpolator` paths: `selectCellYZ`'s filling-cell `Mth.lerp3`, and per-voxel `updateForY`, `updateForX`, `updateForZ` interpolation. A density kernel must retain both orders exactly.

In the async path, workload 6 and static-noise preparation complete before the first slice is initialized. Each slab then prepares workload 4; its continuation consumes the result and performs block mutation on the serial owner. Cleanup aborts interpolation, closes pending result leases, and releases section ownership. Any expanded stage must preserve this ordering and cancellation lifetime; no native worker may retain `NoiseChunk`, `ChunkAccess`, `BlockState`, or world references.

After `fillFromNoise`, the inspected generator still runs carvers, `SurfaceSystem.buildSurface`, structures/features and downstream lighting/chunk save through their existing CPU paths. This audit found no corresponding GPU kernels or consumed GPU outputs for those stages.

## Density graph expansion

The graph's numeric operators are feasible to describe in a bounded, versioned DAG, but the current workload 5 collector does not evaluate graph arithmetic. A first supported opcode set could cover constants, coordinates, `YClampedGradient`, `Clamp`, `Mapped`, `MulOrAdd`, two-argument add/multiply/min/max, `RangeChoice`, `IntervalSelect`, `Noise`, `Shift`/`ShiftA`/`ShiftB`, `ShiftedNoise`, and cubic splines. This is a proposed boundary, not implemented behavior. Start with an explicit whitelist and reject the whole graph batch if a live root contains an unsupported function or runtime wrapper.

The interpreter must match Java's evaluation contract, not just its formulas:

- `Ap2.compute` evaluates argument 1 first. Multiply returns positive zero when that value compares equal to `0.0`; min/max may return argument 1 from range-bound checks before evaluating argument 2, then use `Math.min`/`Math.max`. Preserve short-circuiting, NaN, and signed-zero behavior.
- `RangeChoice` and `IntervalSelect` evaluate the input and only the selected branch; `RangeChoice` uses `>= minInclusive && < maxExclusive`, while interval selection chooses the first threshold for which input is `< threshold`.
- `Mapped` includes square/cube, half/quarter-negative, reciprocal, and `squeeze`; clamping and each multiply/add must round in Java order. Reassociation, fused multiply-add, reduced precision, and quantization are disallowed.
- `Noise` scales integer block coordinates before sampling. `Shift` families use a 0.25 coordinate scale and multiply the sampled value by 4; `ShiftA` forces Y to zero, and `ShiftB` rearranges the coordinates. `ShiftedNoise.compute` first evaluates each shift child and then adds it to the correspondingly scaled block coordinate before sampling its terminal noise. Workload 5 currently does not evaluate this dynamic terminal sample. Supporting it requires staged child evaluation (or a fused topological interpreter), not a static list of guessed coordinates.
- Spline coordinates are cast from `double` to `float`. Knot locations, derivatives, nested spline values, binary-search branch selection, linear extension and cubic interpolation are all float operations in `CubicSpline`; retaining them as doubles changes results. The schema must carry raw float bits and implement the same interval and arithmetic order.
- `NoiseChunk`'s `Cache2D`, `CacheOnce`, `CacheAllInCell`, `FlatCache`, `NoiseInterpolator`, and blender wrappers carry context or mutable cached state. They cannot be replaced by a stateless graph evaluator without modeling which coordinate/context each wrapper observes. Begin with a fixed cell snapshot and a deliberately narrow supported graph; reject non-empty blender/custom nodes until their behavior is represented. Preserve exact-coordinate leaf-cache misses as CPU fallbacks.

`EndIslandDensityFunction` has its own seeded simplex sampler and thread-local cache; `FindTopSurface` has iterative context-dependent sampling. They are outside the first opcode set. Plugin-provided density functions and any unrecognized class are also CPU-only. Returning a partial GPU value while CPU re-evaluates the complete graph would not count as graph offload.

## Aquifer status and classification

The CPU ranking loop examines the 12 centers in X, then Y, then Z order and inserts a new candidate on `oldDistance >= newDistance`; equal distances therefore have a precise later-visit tie order. Distances are computed from signed integer coordinate differences and integer squares. The centers are generated by `positionalRandomFactory.at(gridX, gridY, gridZ)` with three `nextInt` calls, then stored in `aquiferLocationCache`. This random work must stay CPU-owned; the current implementation correctly materializes primitive center coordinates before workload 6.

After ranking, the current `computeSubstance` has early exits for positive density, global fluid above `skipSamplingAboveY`, global lava, nonpositive similarity, and water-over-lava. Otherwise it lazily gets candidate statuses, computes up to three pressure barriers in a fixed order, memoizes one barrier-noise value for the query, and sets `shouldScheduleFluidUpdate` from status equality and the 10/12-distance similarity threshold. Keep these branch orders and the side-channel flag coupled to the exact block query.

Candidate `FluidStatus` is not a small function of the top four indices. `computeFluid` calls the `FluidPicker`, samples 13 chunk offsets of `NoiseChunk.preliminarySurfaceLevel` (quantized through QuartPos and cached by 2D column), may call the picker again at adjusted surfaces, checks deep-dark region from erosion/depth, then evaluates floodedness, spread and lava noises. Surface-level spread uses `floorDiv` cell coordinates, scales noise by 10 and quantizes to thirds; lava uses 64-by-40-by-64 cell coordinates. Statuses are cached lazily by center index. A faithful GPU stage must either evaluate these graph roots from the same immutable graph snapshot and reproduce cache keys, or receive fully materialized primitive inputs. Merely computing pressure on the GPU after the CPU has computed every status leaves the major status work on CPU.

An incremental, coherent path is:

1. Add a workload 7 density-cell batch. Snapshot the two corner slices for one cell slab, compiled graph descriptors, initialized noise profiles, and block contexts. In one FP64 dispatch, reproduce vanilla interpolation and evaluate the complete supported `fullNoiseDensity` DAG per voxel. Feed those density values directly to the aquifer path; do not also run the CPU density graph for accepted queries. If the density graph is not wholly supported, reject that density batch and retain the existing CPU graph. Fusing interpolation and density avoids a CPU readback/re-upload between workloads 4 and 7; a separate second dispatch is a simpler prototype but must include its transfer/launch cost in performance results.
2. Extend the same snapshot model with candidate-center status dependencies and a workload for exact `FluidStatus` construction, pressure barriers, fluid-state code and `shouldScheduleFluidUpdate`. CPU still owns positional RNG, any `FluidPicker` snapshot whose implementation is explicitly known and pure, final block writes, heightmaps, and post-processing marks. Unknown picker or graph types reject the aquifer batch. Multi-dispatch dependencies must be explicit: compute shaders have no global workgroup barrier, so do not assume a status produced by one workgroup is ready to another invocation in the same dispatch.

For the wire format, use a new workload identifier and dedicated shader entry, with a schema version, bounded opcode/DAG tables, profile records, two raw words per binary64 value, raw IEEE float-bit records for spline data, integer XYZ/cell inputs, and a compact fixed-width result per query. Validate node/edge counts, depth, profile references, cell bounds, coordinate ranges and total bytes before dispatch. Keep result ownership and byte budgets in `WorldgenResult`; the shader must receive primitive arrays only.

## What blocks compact final block classification

The useful compact result is not a density alone. It must encode the exact material-rule result (or a bounded palette index), the `shouldScheduleFluidUpdate` bit, and enough distinction to retain default-block, air, water, lava, ore/filler, and debug outcomes. `NoiseBasedChunkGenerator` still applies `debugPreliminarySurfaceLevel`, checks debug-void terrain and AIR, writes section states, updates two heightmaps, and marks fluid blocks for post-processing. Those commits remain CPU-owned.

Ore vein rules are another concrete boundary: `OreVeinifier.create` calls three density functions and a positional `RandomSource`, drawing floats conditionally to choose ore/raw ore/filler. Do not move that rule into a GPU shader without reproducing its seeded per-block choices exactly; for an initial aquifer classifier, leave ore selection on CPU or reject settings that require it. `MaterialRuleList` is ordered and returns the first non-null state, so a GPU aquifer result must retain null-versus-state and allow later CPU rules when null. Surface rules are a later stage and cannot be folded into `fillFromNoise` output.

## Quality gates before calling this GPU coverage

- For every supported operator and full vanilla graph fixture, compare CPU and GPU outputs by raw `Double.doubleToRawLongBits`; spline paths also need raw float-bit checks. Include negative coordinates, cell boundaries, branch thresholds, equal aquifer distances, signed zero/NaN cases, min/max shortcut cases, and shifted coordinates with distinct raw bits.
- Compare the complete aquifer result per voxel: returned block state, fluid-update flag, and post-processing decision against an untouched CPU instance; cover status-cache hits/misses, water/lava transitions, deep-dark and surface early exits, and negative world coordinates.
- Keep fallback explicit. Report submitted, accepted, consumed, stale/rejected, and CPU-fallback counts separately. Only count a saved CPU computation when a GPU result actually drove that sample and the original full graph/pressure branch was not recomputed for parity.
- Run hardware parity on each supported GPU and mixed-device configurations, then fresh-world block/biome/heightmap/fluid/structure/lighting comparisons and save/reload checks. Measure the fused path, including snapshot, dispatch, transfer and CPU commit costs. Keep the 2.0.0 version gate closed until the requested movement/load regressions and end-to-end tests pass; kernel unit parity alone does not establish world or performance parity.
