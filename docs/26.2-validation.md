# GPur 26.2 負荷検証

[日本語](26.2-validation.md) | [English](26.2-validation.en.md)

> このページの実機・負荷表は、以前の1.0.0ビルドと記録された負荷条件を扱う歴史資料です。表は変更していませんが、GPur 1.1.0の検証結果ではありません。現行の根拠と限界は[1.1.0検証記録](1.1.0-validation.md)を参照してください。

GPU結果の採用と無効化の並行処理を修正した版で、CPU・RTX 3070・GTX 1080・混在GPUの4構成を同一条件で測定した。300人を接続し、60人が20Hzで移動する条件では、固定AI 3,000体区間はCPUで4.14 TPS、50ms超tickは129件だった。個別条件の全結果は下表に示す。20 TPSの維持やtick dropゼロは達成しておらず、標準Paper/Purpurとの対照試験もないため、サーバー全体の高速化は立証していない。

最終的な完成判断の基準は「CPU構成と同等以上」に緩和された。ただし、今回の各構成1回の短い測定では、3070のTPS・p50・p95に改善が見られる一方、1080の固定AI区間はCPUより低いTPSとなり、混在構成ではp95・p99が悪化した。通常の自然湧き・AI・GCの揺れも含むため、GPUが原因の差と断定できず、全構成の同等以上も立証できていない。50ms超tickの絶対件数は完了tick数によって変わるため、件数だけを性能差の根拠にしない。

## GPU dispatchとホスト資源

`GPU結果`はrun終了時のGPur per-device/per-workload累計。workload 1はFP64最近傍距離、workload 2はPaper HIDE Anti-Xray整数mask。dispatch数はGPU計算が走った証拠であり、全問い合わせや全tickがGPUで処理された意味ではない。遅いdispatchは30秒backoff後に再評価する。plugin、mob AI、プレイヤー状態更新、イベント、乱数、地形生成、redstone更新はCPU処理のまま。

## CPU負荷の診断

ローカルに保存したsparkの全期間のサンプルでは、`Entity.setPos`が各構成のServer threadサンプルの32.75–33.85%、`runAllTasksAtTickStart`が20.31–21.38%を占めた。CPU構成では`ServerWaypointManager.updateConnection`も17.04%だった。これらは呼び出した処理を含む時間で相互に重なり、配置などのsetupと待機も含む。割合を加算したり、固定AI区間だけの内訳として使ったりしない。[抽出したprofile](results/profiles.json)には各構成の上位メソッドを保持した。

測定はコミット前の最終ソースを使ったため、バージョン文字列の`7448585`は基線コミットを指す。測定時のソースとビルド入力は[Git blob識別子と検査件数](results/build-checks.json)で固定している。負荷試験後、ソースフォルダを`purpur-server`→`gpur-server`、`purpur-api`→`gpur-api`、`purpur-checkstyle`→`gpur-checkstyle`へ移動し、ビルドのパス参照を更新した。履歴として残した測定時blobのパスは移動前のものを示す。コミット後の配布JAR再生成ではGit版情報が更新されるためSHA-256が変わる。上表のSHA-256は実際に負荷を測定したJARの値である。

移動後もMinecraftパッチ240件・Paperパッチ42件の適用を確認し、全build（9,831件、失敗・エラー0、スキップ28）とキャッシュを再利用しない実機GPU検査（38件、失敗・エラー・スキップ0）が成功した。[移動後の検査件数](results/relocated-build-checks.json)と[ソースの同一性](results/relocation-checks.json)を記録した。測定時の453入力中、パスを対応付けた449入力は同一blobで、4入力の差はビルド設定・Checkstyleのパス参照だけである。Paperweightのforkは`serverDirectory`を明示して新しいフォルダからパッチを読み込む。

測定で起動したserver JARと移動後・コミット前のdev JARを展開して比較し、[10,456個のclassと全resourceの内容一致](results/relocated-class-checks.json)も確認した。ZIPの梱包方式によって外側のJAR SHA-256が異なっても、配置移動によるゲーム処理・シェーダーの変更はない。

## 全員移動のpre-backoff診断

300人全員を20Hzで動かしたCPU（`20261007-025406-748100-cpu`）、RTX 3070（`20261007-025921-286200-rtx3070`）、GTX 1080（`20261007-030345-862300-gtx1080`）、mixed（`20261007-030807-557500-mixed`）の4 runは、約60秒のtick停止でwatchdog終了コード70となった。これらはすでに`ServerWaypointManager`両snapshotを`List.copyOf`へ変えた版であり、そのCPU最適化だけでは停止を防げなかった。失敗時stackでは`updatePlayer`/`updateWaypoint`、Guava table entry/column走査、`Entity.setPos`、移動packet処理が観測された。これらはbackoff受け入れ修正前の診断で、今回の20%-walking最終matrixと混ぜない。停止したtickにTickEnd sampleはないため、最後のMSPT値を停止時間として扱えない。
